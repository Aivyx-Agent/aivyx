# Tool System Audit & Catalog (Chapter Atlas)

> **Status:** 🧭 **design contract — AT.0 ✅ + AT.1 ✅ + AT.2 ✅ + AT.3 ✅.** The locked reference for a
> **refinement + catalog** pass over Aivyx's tool system — *no new tool domains*
> this chapter. It produces a generated, drift-guarded **`docs/TOOLS.md` catalog**,
> a runtime **`tools.list` introspection tool**, a **schema/description/error-shape
> QA sweep**, and a documented **tool-name → capability-scope mapping**. Operator
> picked the refinement track over new-tools breadth; new tools (utilities,
> integrations, `git.write`) are a *future* chapter, recorded in §6.

## 1. Why — what the audit found

Aivyx's tool system is large and mature: **~92 `Tool` impls** over **85 capability
bases** (`KNOWN_BASES`), four trust tiers, per-tool-process sandboxing, and an MCP
bridge. The `Tool` trait is clean and security-first — a *pure* `required_scope(input)`
computes the capability the call needs, enforced **before** `execute`. Tools arrive
in three governance tiers (PRODUCT.md **P10**):

- **Substrate (capped at 13, amendment-gated):** fs, net, shell, git, llm, memory,
  web.fetch, skills, … (the irreducible core).
- **Infrastructure (in-process, uncapped):** mission, schedule, webhook, file_watch,
  notify, reflection, persona, skills, loop, role, memory_gc, turn_history, team.
- **Tool processes (out-of-process, Chapter F/G SDK):** gmail, calendar, drive,
  contacts, notion, obsidian, n8n, toolkit (web.search / task.* / health.* /
  budget.*), kitchen.

For all that surface, the audit found four gaps — none about *capability*, all about
*legibility and consistency*:

1. **No tool catalog.** `docs/TOOL_SDK.md` teaches how to *build* a tool; nothing
   lists what tools *exist* — their scopes, tiers, and example inputs. There is no
   single answer to "what can the agent do?"
2. **No runtime tool introspection.** The agent can enumerate its *skills*
   (`skills.list`) but not its *tools*. Local models in particular **hallucinate
   tool names when asked to enumerate** ([[local-model-tool-introspection]]) — a
   first-class introspection tool gives them ground truth.
3. **Implicit name → scope mapping.** Tool `web.fetch` is gated by scope
   `net.fetch`; `gmail.*` tools by `email.*`; etc. Deliberate, but undocumented —
   an operator reading `[role]` scopes can't easily map them to tools.
4. **No cross-tool QA invariant.** With 92 hand-written tools there is no test
   guaranteeing each has a non-empty name/description and a valid `input_schema`
   (the JSON the LLM relies on), nor that tool processes return uniform
   `ToolOutcome` error shapes.

## 2. The enumeration source (what makes this cheap)

`aivyx_core::planner::ToolRegistry` already holds every tool the agent has and
exposes **`snapshot() -> Vec<Arc<dyn Tool>>`**. Each `Tool` exposes `name()`,
`description()`, `input_schema()`, and `required_scope(input)`. So both deliverables
read the *same live data the LLM prompt is built from* (`append_tool_catalog` /
`LlmToolDescriptor` in `profile_prompt.rs`) — the catalog and the introspection tool
cannot drift from reality because they derive from it.

**The one wrinkle:** a `tools.list` tool lives *inside* the registry it would
describe, so it can't hold a strong `Arc<ToolRegistry>` (reference cycle). Resolve
it by handing `tools.list` a **precomputed `Vec<ToolDescriptor>` snapshot** captured
at agent-build time (the tool set is fixed once the agent is assembled), or a
`Weak<ToolRegistry>`. Snapshot is simpler and avoids the cycle entirely — decided in
AT.2.

## 3. Scope — refinement only

**In scope:** the catalog, the introspection tool, the QA sweep, the mapping doc,
and any *small* consistency fixes the sweep surfaces (a thin description, a missing
schema field). **Explicitly out of scope:** new tool domains, new capability bases,
new integrations, and `git.write` (a genuinely *new* destructive tool needing its
own base + amendment — a future "new tools" chapter, §6). This chapter must add **no
new `KNOWN_BASES` entry** except, if AT.2 needs one, a single infrastructure base for
`tools.list` (infrastructure-tier, like `turn.history` — **no P10 amendment**, since
P10 caps *substrate*, not infrastructure).

## 4. Deliverables

### 4.1 `docs/TOOLS.md` — the generated catalog (AT.1)
A single operator/user reference, **generated from the live registry**, listing for
every tool: **name · one-line description · required-scope base · trust-tier default
· governance tier (substrate/infra/process) · a minimal example input**. Grouped by
domain. Generated by an `aivyx tools` CLI subcommand (or a `--catalog` dump) so it is
reproducible, and **drift-guarded by a test** (the repo's established pattern, e.g.
`key_domain_count_matches_docs`): the test regenerates the catalog and asserts it
matches the committed `docs/TOOLS.md`, so a new/changed tool fails CI until the doc is
updated. Includes the **§4.4 name→scope mapping table**.

### 4.2 `tools.list` — runtime introspection (AT.2)
An **infrastructure-tier**, read-only tool that returns the agent's own tool surface
(name, description, scope base, tier) from the build-time snapshot. Optional `filter`
(by domain/substring) and `detail` (include schema) inputs. Directly targets the
local-model hallucination problem — the agent can ask itself "what tools do I have?"
and get ground truth instead of invented names.

### 4.3 Schema / description / error-shape QA sweep (AT.3)
A test over `ToolRegistry::snapshot()` asserting **every** tool has: a non-empty,
dotted `name`; a description over a minimum length; and an `input_schema` that is a
valid JSON-Schema object (`type: object`, declared `properties`). Fix whatever it
flags. Plus a pass confirming tool processes surface failures as uniform
`ToolOutcome` variants (not ad-hoc strings).

### 4.4 Name → scope mapping (AT.1, in `TOOLS.md`)
A table documenting every tool-name → capability-base mapping where they differ
(`web.fetch`→`net.fetch`, `web.post`→`net.post`, `gmail.*`→`email.*`, the
`<service>.*`→`<base>` integration pattern), so an operator reading `[role]` scopes
can map grants to tools.

| **AT.1** ✅ | **`docs/TOOLS.md` + drift-guard** | DONE. Shipped [`docs/TOOLS.md`](TOOLS.md): all tools grouped by domain with scope base · min trust tier · delivery (substrate/infra/tool-process/MCP) · notes, plus the **name→scope mapping table** and a "how tools are delivered / how to read scopes" intro. **Approach adjustment (recorded honestly):** a *live* `ToolRegistry::snapshot()` generator proved impractical — the in-process tool vec is assembled inline + config-conditionally in `aivyx.rs`, the tool-process integrations are out-of-process (not deps of `aivyx-cli`, and wiring 9 in would undo the recent dep cleanup), and several integration tools can't be constructed without live clients/dirs/stores. **Discipline:** AT.1's drift-guard is the chapter's spine — once `TOOLS.md` is
generated-and-guarded, it stays true for free forever, and every later tool change
must touch it. Test band: moderate — dense in AT.2 (a full `Tool` impl) + AT.1/AT.3
(generator + two invariant/drift tests); price ~25–40 new tests, not a coarse label.

## 6. Recommended but deferred — the "new tools" backlog (not this chapter)

Recorded from the audit so it isn't rediscovered; each is a *future* new-tools
chapter, gated by the substrate cap / its own base + amendment where applicable:

- **`git.write`** — the code already flags the read-only-git asymmetry; a destructive
  git tool needs a new `git.write` base (amendment) + sandbox review.
- **Utilities pack** (toolkit): calculator, unit/timezone conversion, date math
  (beyond `time.now`).
- **`web.extract`** — readability/clean-text to complement `web.search`/`web.fetch`.
- **Structured-data readers** — CSV / PDF / spreadsheet.
- **Integrations** (tool processes, need keys): GitHub/GitLab, weather, maps/places,
  Google Tasks/Keep, Microsoft 365.

## 7. Open questions (resolve in-phase, not blockers to AT.0)

- **Catalog generator home** — an `aivyx tools` subcommand (operator-runnable, doubles
  as the drift-guard's generator) vs. a test-only generator. Lean `aivyx tools` (AT.1).
- **`tools.list` registry handle** — build-time descriptor snapshot vs `Weak<ToolRegistry>`
  (AT.2). Snapshot preferred (no cycle, tool set is fixed at assembly).
- **Studio "Tools" view** — nice for discoverability but widens scope to the web; keep
  AT.4 optional / defer to a follow-up.
- **Per-tool examples** — hand-authored (best quality) vs derived from the schema
  (zero-maintenance, lower quality). Decide in AT.1.

---

*Chapter Atlas is the tool system's map: it makes the 92-tool surface legible
(a generated catalog), self-describing (runtime introspection), and consistent
(a QA invariant) — without adding a single new capability. The new-tools breadth it
deliberately defers is the chapter after.*
