# `aivyx-checkpoint` for `git.rs` and `workspace.*` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire `aivyx-checkpoint` protection into `git.commit` (a real repo mutation) and `workspace.write`/`.delete`/`.note` (real filesystem mutations under `workspace_root`) — the two tool families the 2026-08-18/19 `aivyx-checkpoint` adoption left uncovered because neither operates on `fs_root`.

**Architecture:** Both tool families get self-contained, per-tool-family checkpointing — never routed through `ConcreteAgent`'s existing `fs_root`-scoped checkpointer hook, since neither `[git] repos` nor `workspace_root` *is* `fs_root`. `git.commit` gets one `GitCheckpointer` per configured repo, precomputed once at startup into a `HashMap<PathBuf, Arc<GitCheckpointer>>` (repos are a small, fixed, operator-curated allow-set — cheaper to detect once than per call). `workspace.*` gets one `GitCheckpointer` for the single fixed `workspace_root`, built once, mirroring `fs_root`'s own checkpointer exactly. `aivyx-core`'s public builders (`GitWriteToolConfig::build`, `build_workspace_tools`) stay synchronous; the async `GitCheckpointer::detect()` calls happen in the binary (`aivyx.rs`) before construction, matching how `fs_root`'s own checkpointer is already built.

**Tech Stack:** Rust, `aivyx-checkpoint` (`GitCheckpointer::detect`/`checkpoint`), `aivyx_checkpoint::test_support` (test fixtures), `tokio`.

## Global Constraints

- `Tool::mutates_fs_root()` stays `false` (the default) on `GitCommitTool`, `WorkspaceWriteTool`, `WorkspaceDeleteTool`, and `WorkspaceNoteTool` — do not flip it. Checkpointing here is self-contained per tool, not routed through `ConcreteAgent`'s existing `fs_root`-scoped hook (that hook would checkpoint the wrong directory).
- No auto `git init` of `workspace_root`. Checkpointing for `workspace.*` stays opt-in: if `workspace_root` isn't already a git repo, `workspace_checkpointer` is `None` and the three mutating tools get zero checkpoint protection, matching `fs_root`'s existing graceful-degradation contract.
- `GitWriteToolConfig::build()` and `build_workspace_tools()` both stay fully synchronous. No `async fn build` signature change in `aivyx-core`'s public API.
- `WorkspaceReadTool` and `WorkspaceListTool` are not touched — no checkpointer field, no signature change, stay generated by the existing `ws_tool!` macro exactly as today.
- No changes to the `aivyx-checkpoint` crate itself. `GitCheckpointer::detect`/`checkpoint` are used exactly as they exist today.
- `GitStatusTool`/`GitDiffTool` are not touched — read-only, never mutate, never checkpoint.
