## 1. Why — memory has entries, not knowledge

Aivyx remembers in **entries**: small, timestamped, topic-tagged notes.
Recall (Chapter Loom) finds the right entries well. But a topic the agent
has touched fifty times is fifty scattered fragments — there is no
*consolidated* view of "what does the agent know about `deploy`?" Three
costs follow:

1. **No legible knowledge surface.** The Studio Memory screen lists
   entries; it can't show "here is the synthesized state of this topic."
   An operator auditing what the agent believes must read raw fragments.
2. **Recall injects fragments, not understanding.** Loom fuses the most
   relevant *entries*; for a broad query, five entries about `deploy` cost
   five slots and still under-cover the topic. One consolidated paragraph
   would be higher-signal per token.
3. **The graph has no anchor.** Chapter MG draws topic nodes and
   co-occurrence edges, but a node is just a label — clicking it shows
   entries, not a *page*. The graph wants pages to link between.

A **wiki page per topic** closes all three: a living summary (the
artifact), navigable by the graph's edges (backlinks), that doubles as a
retrieval unit. It is the natural consolidation layer over the entry
substrate — "entries are what happened; pages are what is known."

## 2. Architecture & decisions (locked)

### The page model
A `WikiPage` is keyed by **canonical topic** (reusing the Phase 89 / Loom
topic canonicalizer so `deploy`/`deploying` share one page) and holds:
`{ topic, summary, source_seqs, backlinks, entry_count, updated_at,
source_fingerprint }`. The **`source_fingerprint`** (a cheap hash of the
contributing entry seqs + count) makes regeneration **incremental** — a
topic whose entries haven't changed since its page was built is skipped,
so synthesis cost scales with *churn*, not corpus size.

### Synthesis is best-effort LLM consolidation
A `WikiSynthesizer` pulls a topic's entries, prompts the daemon's existing
`Arc<dyn LlmProvider>` to consolidate them into a concise, factual summary
(assembling the streamed response), and writes the page. **Best-effort and
non-blocking:** no LLM provider configured, an LLM error, or an empty
topic → the page is skipped, never errored — memory, recall, and the turn
are untouched (the same contract Loom recall and reflection already hold).
Synthesis never *invents*: the prompt constrains the model to consolidate
only what the entries say, flagged as background knowledge.

### Backlinks reuse the co-occurrence graph (no new graph)
A page's `backlinks` are the topic's strongest neighbors from the Phase 83
ledger via Loom's **`neighbors_within`** — the same weighted multi-hop
walk, reused as-is. The codex adds **no new graph model and no typed
edges** (that is the still-deferred "real DAG" chapter). It gives the
existing graph the *pages* its nodes were missing.

### Storage: one new domain, persisted
Pages live in a new HKDF-isolated **`KeyDomain::KnowledgeWiki`**, keyed by
canonical topic. Persisted (not recomputed per read) so the Studio and
recall read them cheaply; a corrupt/missing page degrades only the codex,
never memory. Routine storage growth (enum variant + `ALL` + subkey +
count-test bump), the same shape every prior domain followed.

### Generation rides the reflection cadence + an explicit rebuild
Pages are regenerated by a **stale-sweep** that runs on the existing
reflection scheduler cadence (the same loop that already fires
consolidation work), plus an explicit rebuild entrypoint for on-demand
refresh. Incremental fingerprinting keeps each sweep cheap. No new
always-on loop — it reuses the cadence the daemon already runs.

### Recall integration: a page is a retrieval unit, fused via Loom
A wiki page's summary becomes a **candidate in Loom's RRF fusion** — a
single consolidated unit competing alongside the semantic / lexical /
graph entry rankers. Built directly on Loom's `reciprocal_rank_fusion_
weighted`; gated by a new opt-in `[embedding]` knob, **byte-identical
default off**, recall-never-errors preserved. A consolidated summary often
out-covers five fragments per token — but only when the operator opts in.

### Governance: infrastructure, not a new operator tool
The codex is the agent organizing **its own** memory — P10's
*infrastructure* tier (like reflection / consolidation), **not** a new
operator-facing substrate tool. So: **no P10 substrate-count amendment, no
new capability base.** Studio reads go over **read-only IPC** (new
`ListWikiPages` / `GetWikiPage`), exactly like the R→Z Studio screens.
Synthesis uses the existing daemon LLM provider. Lighter governance than a
tools chapter — the contract here is the page model, the storage domain,
and the recall opt-in, verified by tests.

## 3. Scope

**In:** the `WikiPage` model + `KnowledgeWiki` storage, the LLM
consolidation engine + graph backlinks, incremental fingerprinting, the
cadence stale-sweep + explicit rebuild, the read-only IPC, the Studio Wiki
screen, and the opt-in recall-unit fusion.

**Out:** typed/directed entity–relation edges + extraction (the deferred
"real DAG" chapter); editing pages by hand (pages are *derived* — the
source of truth is memory; correct a page by correcting memory); any new
operator substrate tool or capability base; multi-language summary
tuning. No change to the memory entry model, the ledger, or Loom's fusion
math beyond adding the page source.

**Discipline:** CX.1–CX.2 ship the page substrate **inert**; CX.3 is the
first behavior (generation), gated to the existing cadence and best-effort;
CX.6's recall change is opt-in + default-off like every Loom seam. Each
read/write boundary (storage, IPC, recall) lands behind its own phase so
the diff at each step stays reviewable. Pages are always **derived** — at
no point does the codex become a second source of truth the operator must
maintain.

## 5. Open questions (resolve in-phase)

- **Summary length / shape** — a tight paragraph vs. a few bullet facts.
  Default to a short paragraph capped to a token budget the recall unit can
  afford; revisit against the CX.6 eval (CX.2/CX.6).
- **Stale threshold** — regenerate when entry-count or max-seq moved at
  all, or only past a churn threshold (e.g. N new entries)? Default to any
  change with a per-sweep page cap so a busy topic doesn't dominate (CX.3).
- **Backlink depth** — 1-hop (direct siblings) vs. Loom's multi-hop for
  page links. Default 1-hop for a clean page; the walk's `hops` is
  available if richer linking proves useful (CX.2/CX.5).
- **Recall unit granularity** — inject the whole summary, or let the token
  budget truncate it like an entry body? Default: treat the summary as one
  body, subject to the existing Phase 97 budget (CX.6).

---

*Chapter Codex turns the agent's memory from a pile of entries into a
**book it keeps about itself** — one page per topic, written from what it
remembers, cross-linked by what goes together, and readable both by the
operator (the Studio) and by the agent (recall). Entries are what
happened; the codex is what is known.*
